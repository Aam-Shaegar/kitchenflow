# Как устроен KitchenFlow

## Процессы и зависимости

`cmd/kitchen-api` собирает HTTP-маршруты на стандартном Go ServeMux, middleware, сервисы и PostgreSQL-репозитории. В этом же процессе работает фоновое восстановление отправки заказов. `cmd/restaurant-mock` — отдельный HTTP-процесс с имитацией кухни. Клиентское приложение в репозиторий не входит.

Код сгруппирован по функциям внутри `internal/features`. У сервисов есть интерфейсы для зависимостей, но модули связаны и на уровне импортов. Корзина использует тип блюда из меню. Сервис заказов принимает репозиторий корзины, интерфейсы чтения меню и ресторана и клиент интеграции. Обработчик callback вызывает сервис заказов. Мок использует общие правила смены статусов. В `internal/core` находятся HTTP-инфраструктура, проверка подписи, работа с PostgreSQL, миграции, журналирование и проверки готовности.

## Корзина и оформление

У пользователя одна активная корзина. Транзакции изменения корзины берут блокировку по пользователю. Пока корзина непуста, добавить блюдо другого ресторана нельзя. Количество одной позиции ограничено диапазоном 1–50. Цены хранятся в целых копейках.

При оформлении сервис повторно читает меню. В заказ попадают цена на момент оформления, название и внешний ID блюда. Изменение цены после добавления в корзину может изменить итог заказа. Заказ, позиции, первая запись истории и задание отправки сохраняются в одной транзакции с удалением исходной корзины. Проверка ревизии корзины защищает от оформления устаревшего снимка. Конфликт возвращает HTTP 409. Повтор запроса с тем же ключом для того же пользователя возвращает сохранённый заказ.

## Отправка и статусы

Первую отправку API пытается выполнить синхронно после фиксации заказа. Отсутствующий или запрещённый адрес ресторана даёт 503 до создания заказа. Если ресторан недоступен уже при отправке, клиент может получить 201 с заказом в состоянии `integration_failed`. Заказ сохраняется. Повторная отправка использует исходные позиции и ID заказа. Для старых заказов без сохранённых внешних ID блюд явный retry возвращает 409 до ручной сверки.

Каждый экземпляр API опрашивает таблицу `order_dispatch`. Воркер забирает доступное задание с временной арендой и может восстановить отправку после перезапуска. Сетевой запрос может повториться. За дедупликацию на своей стороне отвечает ресторан.

Обычный путь — `pending → confirmed → preparing → ready → delivering → delivered`. Ресторан может отказать в принятии заказа. Пользователь может запросить отмену до начала приготовления. После подтверждения ресторана API сохраняет `cancelled`. Отказ в отмене даёт 409, а неопределённый результат — 503. После сбоя отмену повторяет клиент. Фоновый воркер восстанавливает отправку заказа ресторану.

Callback проверяется по подписи и ресторану. Проверка повтора по `event_id`, обновление заказа и запись истории происходят под блокировкой в одной транзакции. История хранит события. Например, HTTP-ответ ресторана и следующий callback с новым ID могут оба записать статус confirmed. Повтор уже принятого события получает 204. Повтор ID с другими данными или недопустимый переход получает 409. Запоздалый ответ на отправку не откатывает уже принятый статус.

## Хранение и эксплуатация

API применяет ожидающие SQL-миграции по имени в общей транзакции под advisory lock. Реестр хранит имена применённых файлов. Изменения схемы поставляются новыми миграциями. Проверка `/api/v1/health/live` показывает, отвечает ли HTTP-процесс. `/api/v1/health/ready` и её алиас `/api/v1/health` проверяют реестр миграций и доступность нужных таблиц и колонок. Готовность API не проверяет доступность ресторанов.

Каждая страница заказов читается в отдельной транзакции REPEATABLE READ. Заказы отсортированы по времени создания и ID по убыванию. Между запросами страниц добавление заказов может сместить offset.

Мок поддерживает режимы `auto`, `manual`, `rejecting` и `failing`. Его заказы, дедупликация и очередь callbacks хранятся в памяти. Перезапуск теряет это состояние. Недоставленное событие блокирует следующие события очереди, пока получатель не вернёт 2xx. Долговечность заказов KitchenFlow обеспечивается PostgreSQL. Демонстрационные пароли, открытые порты и настройки сети Compose предназначены для локального запуска.
