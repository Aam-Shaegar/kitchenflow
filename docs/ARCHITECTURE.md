# KitchenFlow — как устроен проект. Полный разбор для стажера

Этот документ объясняет проект так, чтобы после прочтения ты мог собрать такой же
с нуля, не повторяя чужих ошибок. Здесь нет магии: только причины каждого решения,
разбор каждой папки и каждого файла, а также честный список того, что мы нашли
ручной проверкой всех 49 запросов и как это чинили.

Формат: сначала принципы, потом сквозной путь запроса, потом папка за папкой
и файл за файлом, потом паттерны и антипаттерны, потом инструкция «построй такое же».

---

## 0. Карта проекта за 60 секунд

```
KitchenFlow
├── cmd/                    # две точки входа: кухня и ресторан-заглушка
│   ├── kitchen-api/        # основной backend (настоящий продукт)
│   └── restaurant-mock/    # пример заведения (учебный, но честный)
├── api/openapi.yaml        # контракт: единственный источник правды для фронта
├── migrations/             # SQL-схема + сиды, применяются сами при старте
├── internal/core/          # общее техническое: конфиг, логер, БД, HTTP
├── internal/features/      # бизнес: рестораны, меню, корзина, заказы, интеграция
├── docs/                   # домен, диаграммы, этот разбор
└── scripts/e2e.sh          # сквозной дымовой тест через curl
```

Главное правило структуры: `core` ничего не знает про бизнес, а `features`
ничего не знают про чужие внутренности. Связывает их только `cmd/kitchen-api/main.go`
(Composition Root — единственное место, где все собирается вместе).

## 1. Откуда растут требования

Требования (`docs/requirements.md`) описывают MVP доставки еды:

1. **API для заведений** — закрытый доступ, прием заказов.
2. **API для web-клиента** — витрина, меню, корзина, заказ (без авторизации в MVP).
3. **Пользовательские сценарии (CJM)** с обеих сторон — гость и ресторан.
4. **Пример заведения** отдельным сервисом в том же репо через Docker Compose.
5. **Миграции + OpenAPI** как артефакты масштабирования.
6. **Линтер**, `docker compose up`, README с C4 и схемой БД.

Архитектура отвечает на это буквально:

- витрина и checkout — `restaurants`, `menu`, `cart`, `orders`;
- сторона заведения — `integrations/restaurant` (колбэки) + портал (`POST/PATCH /restaurants`,
  CRUD меню, `GET /restaurants/{id}/orders`);
- сценарии — `docs/cjm-user.puml`, `docs/cjm-restaurant.puml`;
- пример заведения — `cmd/restaurant-mock`;
- масштабирование — `migrations/` + `api/openapi.yaml` + версионирование API `/api/v1`.

Почему это важно для крупного бизнеса: каждый следующий ресторан, город и фронт
подключаются к тем же контрактам, а не требуют переписывания ядра.

## 2. Семь принципов, по которым собран проект

### Принцип 1. Вертикальные слайсы вместо слоев

Классическая ошибка новичка — разложить код по слоям `handlers/services/repositories`
на весь проект. Тогда изменение «корзины» расползается по трем общим папкам.

У нас наоборот: `internal/features/cart/` содержит свои domain, repository, service
и transport. Хочешь понять корзину — открываешь одну папку. Хочешь удалить заказы —
удаляешь одну папку. Слои остались, но внутри фичи, а не поперек проекта.

### Принцип 2. Зависимости смотрят внутрь

Правило: `transport -> service -> domain <- repository`. Сервис не импортирует
HTTP и не импортирует pgx. Репозиторий знает SQL, но не знает HTTP. Домен не знает
ничего. Поэтому бизнес-правила можно тестировать без базы и без сети, а базу можно
заменить, не трогая сервис.

Проверка принципа: `go vet` и сборка падают, если сервис импортирует `net/http`
или `pgx`. Мы держим это руками, а не на словах.

### Принцип 3. Фичи общаются через интерфейсы, а не напрямую

`cart` не импортирует `menu`, `orders` не импортирует `restaurants`. Вместо этого
в сервисе объявляется узкий интерфейс (`MenuProvider`, `RestaurantProvider`),
а реализация подставляется в `main.go`. Так корзина зависит от «способности отдать
товар по id», а не от всего модуля меню. Заменить меню на внешний каталог можно
одной строчкой в Composition Root.

### Принцип 4. Домен — единственный владелец правил

Проверка «можно ли перейти из pending в delivered» живет в
`internal/features/orders/domain`, а не в хендлере и не в SQL. Хендлер только
переводит HTTP в вызов сервиса, репозиторий лишь пере-проверяет под локом строки.
Одна таблица переходов — один источник правды. Дублирующая `CanTransitionInDB`
была удалена именно поэтому: два источника правды всегда расходятся.

### Принцип 5. Деньги — целое число, всегда

Все суммы — `BIGINT`/`int64` в копейках. Float запрещен везде: в Go, в Postgres,
в OpenAPI. Причина прозаична: `0.1 + 0.2 != 0.3` во float, а в деньгах такая
ошибка — это суд. Копейки складываются точно, чеки сходятся, бухгалтерия спокойна.

### Принцип 6. Ошибки — это контракт, а не текст

Четыре смысловых исхода: `ErrInvalidArgument -> 400`, `ErrNotFound -> 404`,
`ErrConflict -> 409`, все остальное `-> 500`. Хендлер никогда не придумывает код
сам, он вызывает `ErrorResponse`, а та маппит sentinel-ошибки. Нарушение автомата
состояний — это тоже 409 (конфликт бизнес-правила), а не 500. Кривой UUID — 400,
а не 500. Пустой обязательный заголовок — JSON-ошибка 400, а не пустой body.

### Принцип 7. Идемпотентность везде, где есть сеть

Сеть повторяет запросы. Поэтому повторный `POST /orders` с тем же
`Idempotency-Key` возвращает тот же заказ (`UNIQUE(user_id, idempotency_key)`),
а повторный колбэк с тем же `event_id` — пустой успех 204
(`UNIQUE WHERE event_id IS NOT NULL`). Без этого двойной клик создавал бы два
заказа, а ретрай ресторана — две записи истории.

## 3. Сквозной путь одного заказа

Разберем `POST /api/v1/orders`, потому что в нем видно все принципы сразу.

1. **Маршрут.** `cmd/kitchen-api/main.go` регистрирует
   `POST /orders` с мидлварями `RequireHeader("X-User-ID")` и
   `RequireHeader("Idempotency-Key")`. Нет заголовка — сразу JSON 400, до сервиса
   дело не доходит.
2. **Транспорт** (`orders/transport/http/handler.go`). Достает `X-User-ID`,
   `Idempotency-Key`, декодирует `delivery_address` через `DecodeAndValidateRequest`.
   Любая ошибка декода/валидации уже обернута в `ErrInvalidArgument` — будет 400.
   Сам хендлер не знает SQL и не решает, можно ли создать заказ.
3. **Сервис** (`orders/service/service.go`, `CreateOrder`).
   - Проверяет ключи и адрес (5..500 символов).
   - Смотрит, нет ли уже заказа с таким ключом — если есть, возвращает его.
   - Читает корзину, перечитывает товары из меню (цена могла измениться),
     проверяет доступность, один ресторан, количество 1..50, открыто ли заведение.
   - Считает итог в копейках (`price * qty`, `int64`), кладет снепшоты
     названия и цены в `order_items` — чек переживет любое редактирование меню.
   - Пишет заказ + товары + историю `pending` одной транзакцией
     (`CreateWithIdempotencyKey`, `ON CONFLICT DO NOTHING`). Гонку двух кликов
     разруливает база, а не код.
   - Зовет ресторан по HTTP. Упал ресторан — заказ остается в
     `integration_failed`, его потом поднимет `POST /orders/{id}/retry`.
     ID корреляции сохраняется до HTTP-запроса. Успех — согласует статус ответа с уже полученными колбэками, пишет историю и удаляет корзину в одной транзакции.
   - Перечитывает заказ из БД, чтобы вернуть настоящие `id` истории
     (а не in-memory `0`).
4. **Репозиторий** (`orders/repository/postgres.go`). Только SQL через узкий
   интерфейс `core/database.Pool`. Ошибку «нет строк» превращает в `(nil, nil)`,
   уникальный конфликт — в `ErrUniqueViolation`, чужой ключ — в
   `ErrViolatesForeignKey` (см. `pgx/adapters.go`). Сервис решает по смыслу,
   а не по тексту ошибки Postgres.
5. **Ресторан** (`cmd/restaurant-mock`). Принимает заказ, отвечает 201,
   потом шлет колбэки `confirmed -> preparing -> ready -> delivering -> delivered`
   с уникальными `event_id`.
6. **Колбэк** (`integrations/.../handler.go` + `HandleRestaurantCallback`).
   Проверяет `event_id` и статус, ищет заказ по паре
   `(external_order_id, restaurant_id)`, сверяет переход с доменным автоматом,
   пишет под `SELECT ... FOR UPDATE`. Дубликат — 204, прыжок через состояние — 409.

Почему именно так, а не «попроще»? Попроще — это писать заказ без транзакции,
считать деньги во float и верить первому ответу сети. Такой код проходит демо
и разваливается в проде на первом же дабл-клике, ретрае и правке меню.

## 4. Папка за папкой, файл за файлом

### 4.1. `cmd/` — точки входа, больше ничего

**Почему отдельная папка.** Бинарников два, доменов ноль. В `cmd` живет только
сборка и запуск. Бизнес-логики здесь нет по определению — ее некуда положить,
чтобы не соблазнять.

**`cmd/kitchen-api/main.go` — Composition Root.**
Читается сверху вниз как сценарий запуска: конфиг, часовой пояс, контекст
отмены по SIGINT/SIGTERM, логер, пул Postgres, миграции, репозитории, сервисы,
HTTP-клиент ресторана, хендлеры, роутер, сервер. Здесь и только здесь фичи
встречаются друг с другом: `NewOrderService(repo, cartRepo, menuSvc, restaurantsSvc,
restaurantClient)` — это ручная подстановка зависимостей без фреймворка.
Почему без DI-фреймворка: для двух сервисов он дает больше магии, чем пользы,
а явные конструкторы читаются стажером за минуту.

Маршруты тоже здесь: один `APIVersionRouter(v1)` и плоский список `NewRoute`.
Версионирование через префикс `/api/v1` позволяет выкатить `/api/v2`, не ломая
старых клиентов. Мидлвари порядка `CORS -> RequestID -> Logger -> Trace -> Panic`
тоже заданы здесь: сначала контекст запроса, потом все остальное.

**`cmd/restaurant-mock/main.go` — честная заглушка заведения.**
Внутри: типы запросов/ответов, `MockStore` на мьютексе (потокобезопасная память),
`MockConfig` из env, хендлеры заказов/меню/здоровья, `simulateOrderProcessing`
и `sendCallback`. Режимы `MOCK_MODE`: `auto` (сам доводит до delivered),
`manual` (ждет ручного `POST .../status`), `rejecting` (отменяет),
`failing` (отвечает 503). Отдельный `MOCK_DELAYS` задает паузы между статусами.

Почему мок такой взрослый? По ТЗ нужен «пример заведения», а для крупного бизнеса
нужен тренажер: продажи показывают happy path, поддержку учат на `rejecting`
и `failing`, разработку — на `manual`. Важная деталь: отказ тоже начинается
с 201 и `external_order_id`, а отмена приезжает колбэком — иначе Kitchen не смогла
бы связать отказ со своим заказом, и переход `pending -> cancelled` был бы
невозможен. Удаленные велосипеды `nopCloser` заменены на обычный `bytes.Reader`:
`http.NewRequest` сам принимает `io.Reader`, обертка была мертвым кодом.

### 4.2. `api/openapi.yaml` — контракт важнее кода

Единственный источник правды для фронта и партнеров. Описывает все 20+ путей,
схемы, пагинацию (`limit 1..100`, `offset`), деньги как `integer` в копейках,
ошибки `Error{message, error}`. Теги разделены честно: `Restaurants/Menu/Cart/Orders`
для витрины, `Restaurant Portal` для закрытого API партнеров, `Restaurant Integration`
для колбэков. Health лежит в `Restaurants` — исторический компромисс, не идеал,
но менять тег сейчас значит ломать сгенерированные клиенты.

Почему контракт первичен: фронт и ресторан могут разрабатываться параллельно
с бэком, а ручная проверка (раздел 8) сверяется именно с этим файлом.

### 4.3. `migrations/` — схема как код

- **`001_init.sql`** — вся схема с нуля: `restaurants`, `menu_categories`,
  `menu_items`, `carts` (`UNIQUE(user_id)` — одна активная корзина),
  `cart_items`, `order_status` (ENUM с 8 состояниями), `orders`
  (`UNIQUE(user_id, idempotency_key)` — физическая идемпотентность,
  `UNIQUE(restaurant_id, external_order_id)` — связь с заведением),
  `order_items` (снепшоты), `order_status_history` (`BIGSERIAL id`,
  partial-unique по `event_id`), индексы под реальные запросы
  (`orders(user_id, created_at)`, `orders(restaurant_id, status, created_at)`).
  Деньги везде `BIGINT`, количества `1..50`, адрес `5..500` — ограничения живут
  в базе как последний рубеж, даже если сервис забудет проверить.
- **`002_seed.sql`** — демо-ресторан, 3 категории, 7 позиций в копейках
  (`54900` = 549 ₽). `ON CONFLICT DO NOTHING` делает сид безопасным для повторов.
- **`003_money_minor_units.sql`, `004_single_cart_per_user.sql`** — пример эволюции
  живой базы: старые `NUMERIC` превращаются в копейки, старые мульти-корзины
  схлопываются в одну. Идемпотентные `DO`-блоки позволяют гонять их повторно.

Почему файлы, а не ORM-автомиграции: SQL читается DBA, ревьюится и повторяется
на любом стенде одинаково. Порядок — лексический, учет — таблица
`schema_migrations` (см. мигратор ниже).

### 4.4. `internal/core/` — общее техническое, без бизнеса

**`core/errors/common.go`.** Четыре сентиела: `ErrInvalidArgument`,
`ErrNotFound`, `ErrConflict`, `ErrUnauthorized` (+ `ErrInternal` про запас).
Почему свои, а не строки: `errors.Is` переживает оборачивание через `%w`,
а сравнение строк ломается от первой же правки текста. Весь HTTP-маппинг
держится на этих четырех значениях.

**`core/config/config.go`.** Конфиг кухни: часовой пояс, `DATABASE_URL`
(обязателен — падать сразу, а не в первом запросе), `SERVER_ADDR`,
`SHUTDOWN_TIMEOUT`. `NewConfigMust` паникует на старте: лучше не стартовать,
чем стартовать криво. Почему `os.Getenv`, а не YAML: двенадцатифакторное
приложение едет в Docker/K8s именно env-переменными.

**`core/logger/` (`logger.go`, `config.go`).** Обертка над zap: пишет одновременно
в stdout (для Docker) и в файл с timestamp-именем (для разбора полетов).
`ToContext/FromContext` несут логер с `request_id` через контекст запроса.
`With` делает дочерний логер, `Close` закрывает файл. `FromContext` паникует
без логера — это осознанно: тихий запрос без логов хуже громкого падения
на старте разработки. Почему обертка, а не zap напрямую: бизнес-код зависит
от маленького интерфейса логера, а не от всего zap; заменить бэкенд — один файл.

**`core/database/` (`pool.go`, `config.go`, `pgx/*`, `migrate/*`).**
`pool.go` — узкие интерфейсы `Pool/Tx/Rows/Row`: бизнес видит только
«запрос/строка/транзакция», а не весь pgx. Это и есть Dependency Inversion:
сервис зависит от абстракции, реализация — от деталей.

- `pgx/config.go` — `DATABASE_URL` + `DB_TIMEOUT` через envconfig, строго required.
- `pgx/pgxpool.go` — создание пула + `Ping` на старте (не пускаем сервис без базы).
- `pgx/adapters.go` — перевод ошибок pgx в наши сентиела: `ErrNoRows`,
  `23503 -> ErrViolatesForeignKey`, `23505 -> ErrUniqueViolation`. Почему здесь:
  только этот файл знает коды Postgres; остальной код работает со смыслом.
- `migrate/migrate.go` — `Run`: создает `schema_migrations`, читает `*.sql`
  по имени, пропускает примененные, выполняет новые, записывает факт.
  Почему свой, а не `docker-entrypoint-initdb.d`: initdb срабатывает только
  на пустом volume и молча пропускает обновления. Наш мигратор сходится к одной
  схеме и на свежей, и на годовалой базе при каждом старте.

**`core/http/` — транспортное ядро.**
- `request/decode.go` — `DecodeAndValidateRequest` (JSON + validator, любая
  проблема уже обернута в `ErrInvalidArgument`) и `ParseUUID` (кривой UUID —
  всегда 400, а не 500; именно этот хелпер закрыл 8 мест, где раньше тек 500).
- `response/handler.go` — `ErrorResponse` маппит сентиела в коды и пишет
  стабильный JSON `{message, error}`, `JSONResponse` ставит content-type,
  `NoContentResponse` — 204, `PanicResponse` — 500 при панике.
  `isTransitionConflict` узнает отказ автомата по тексту ошибки — осознанный
  компромисс: импортировать домен в core нельзя (будет цикл), а текст ошибки
  стабилен и покрыт тестами. Велосипедные `contains/search` удалены в пользу
  `strings.Contains`.
- `response/writer.go` — обертка, запоминающая status code для логов.
- `middleware/middleware.go` — тип `Middleware` и `ChainMiddleware` (применение
  справа налево, как матрешка).
- `middleware/common.go` — `RequestID` (генерирует, кладет в header и ответ),
  `Logger` (кладет логер с request_id в контекст), `Trace` (входящий/исходящий
  с латентностью), `Panic` (ловит панику в 500), `RequireHeader` (нет заголовка —
  JSON 400, а не пустой ответ), `CORS` (разрешает `X-User-ID` и `Idempotency-Key`,
  иначе браузерный фронт не пройдет preflight).
- `server/` — `config.go` (адрес + таймаут шатдауна), `route.go` (`Route{Method,
  Path, Handler, Middleware}` + `WithMiddleware`), `router.go`
  (`APIVersionRouter`, паттерн `"METHOD /path"` для Go 1.22+; мертвые `v2/v3`
  удалены — версия появится, когда будет вторая), `server.go` (`Run`:
  старт в горутине, graceful shutdown по контексту с таймаутом).

### 4.5. `internal/features/` — бизнес по вертикалям

**`restaurants/` — витрина и портал партнеров.**
- `domain/models.go` — `Restaurant` (полная карточка), `RestaurantInfo`
  (узкий вид для заказов — заказу не нужен `integration_base_url`),
  `RestaurantListItem` (узкий вид для списка). Три вида вместо одного —
  это не бюрократия, а защита: лишние поля не утекают наружу и не тащатся в запросы.
- `repository/` — `GetByID`, `List/ListOpen/ListPaginated`, `Create`, `Update`.
  Пагинация в SQL (`LIMIT/OFFSET`), а не срезом в памяти — для каталога из
  тысяч заведений это разница между миллисекундами и падением.
- `service/service.go` — `GetByID` (nil → `ErrNotFound`), `GetInfoByID`,
  `List/ListFiltered/ListFilteredPaginated` (санитизация лимитов, пусто → `[]`,
  а не `null` — фронт не должен ветвиться), `Create` (имя обязательно,
  `external_id` генерируется при пустом, новый всегда открыт),
  `Update` (патч по указателям: `nil` — не трогать). Мертвый
  `RestaurantServiceInterface` удален: интерфейс ради интерфейса — мусор.
- `transport/http/` — `ListRestaurants` (`?open`, `?limit`, `?offset`),
  `GetRestaurant`, `CreateRestaurant`, `UpdateRestaurant` + `helpers.go`
  (`decodeJSON`, `errInvalid`) и свой `parsePagination` (дубль с orders —
  осознанный: два пакета не должны тянуть общий HTTP-хелпер ради 10 строк;
  связность важнее сухости).

**`menu/` — каталог заведения.**
- `domain/models.go` — `MenuCategory` (с вложенными `Items` для витрины),
  `MenuItem` (цена — копейки), `Menu` (корень ответа витрины).

## 5. Решения, за которые не стыдно перед крупным бизнесом

### Деньги в копейках
`float64`/`NUMERIC` заменены на `BIGINT`/`int64` везде: схема, Go, OpenAPI, сиды,
мок. Миграция `003` переводит старые базы (`*100` с округлением). После прочтения
дока стажер должен вынести одно: деньги во float — это баг, а не упрощение.

### Одна активная корзина
`UNIQUE(user_id)` + `409` на смешивание ресторанов + `DELETE /cart`. Альтернатива
«мультикорзина» была отвергнута: она плодит вопросы «какую оформлять?»,
«куда класть?» и превращает checkout в угадайку. Один инвариант в базе сильнее
десяти проверок в коде. Миграция `004` схлопывает старые дубликаты.

### Автомат состояний с одной таблицей
`pending -> confirmed -> preparing -> ready -> delivering -> delivered`,
отмена только из `pending/confirmed`, `integration_failed` — тупик до retry.
Таблица в `domain.CanTransition`, репозиторий лишь пере-проверяет под
`FOR UPDATE`. Хендлеры переходов не знают вовсе. Добавить `refunded` завтра —
значит дописать две строки в одну таблицу, а не искать `if` по всему проекту.

### Двойная идемпотентность
Заказы — `UNIQUE(user_id, idempotency_key)` + `ON CONFLICT DO NOTHING`.
Колбэки — partial-unique по `event_id` + проверка до перехода. Порядок важен:
дедуп раньше валидации перехода, иначе реплей станет ложным 409.

### Снепшоты цен
`order_items` хранят имя и цену на момент checkout. Меню может дорожать,
переименовываться и удаляться — чеки не поплывут. Цена в корзине — тоже снепшот
момента добавления, а итог заказа считается из свежего меню (защита от
«положил за 100, купил за 100 после подорожания до 200» — нет, купит за 200).

### Мигратор вместо initdb
`docker-entrypoint-initdb.d` работает только на пустом volume. Наш `Run`
с таблицей `schema_migrations` доводит любую базу до актуальной схемы при каждом
старте. Свежая и годовалая базы сходятся к одному состоянию — это и есть
«масштабирование после MVP» из задания.

### Портал vs интеграция
Два разных API не случайно: портал (`POST /restaurants`, CRUD меню,
`GET /restaurants/{id}/orders`) — это кабинет партнера под нашим контролем;
интеграция (`POST /restaurant/orders` наружу, колбэки внутрь) — это граница
с чужим кодом. Смешивать их — значит дать чужому ресторану ключи от каталога.

### Мок как тренажер
Четыре режима покрывают четыре разговора с бизнесом: «все хорошо» (auto),
«повар думает» (manual), «отказываем» (rejecting), «лежим» (failing).
Маркер `reject` в адресе позволяет демоить отказ без переключения env.

## 6. Паттерны и как не наделать ошибок

**Паттерны, которые тут работают:**
- Vertical Slices — фича как единица изменения.
- Composition Root — зависимости собираются в одном `main`.
- Dependency Inversion — сервис зависит от `MenuProvider`, а не от pgx.
- Repository — SQL живет за интерфейсом, ошибки переводятся в смысл.
- Idempotency Key / Deduplication — сеть ненадежна, ключи обязательны.
- Audit Trail — `order_status_history` пишет каждое движение, история — API.
- Fail Fast — кривой конфиг роняет старт, а не первый запрос.
- Graceful Shutdown — `SIGINT/SIGTERM` + таймаут, без обрубленных соединений.

**Ошибки новичка и как архитектура их ловит:**
- «Проверю переход в хендлере» — нельзя: хендлер не знает автомат, домен знает.
- «Сравню float-цены» — не с чем: float нет в типах, код не скомпилируется в ложь.
- «Верну 500 на кривой UUID» — не выйдет: `ParseUUID` уже обернул в 400.
- «Забуду заголовок — пустой 400» — не выйдет: middleware пишет JSON.
- «Создам второй заказ дабл-кликом» — база откажет через unique, сервис вернет первый.
- «Отправлю колбэк дважды» — второй станет тихим 204.
- «Положу суши в бургерную корзину» — 409 и требование очистить.
- «Удалю товар из меню — испортится история» — `RESTRICT` остановит, снепшоты целы.
- «Напишу `if` перехода в репозитории» — репозиторий вызывает `domain.CanTransition`.
- «Импортирую pgx в сервис» — ревью и `go vet` заметят чужой импорт.
- «Добавлю фичу в core» — core не импортирует features; цикл импортов не соберется.

## 7. Как построить такой же с нуля (план для стажера)

1. Напиши OpenAPI первым: пути, деньги-копейки, ошибки. Контракт раньше кода.
2. Нарисуй ERD и CJM в PlantUML: сущности, уникальности, пути гостя и ресторана.
3. Заведи `migrations/001_init.sql` с ограничениями (unique, check, FK) — база как
   последний рубеж.
4. Скелет Go: `cmd/kitchen-api`, `internal/core` (errors, config, logger,
   database-интерфейсы, http-ядро), по одной фиче за раз (restaurants → menu →
   cart → orders → integrations).
5. В каждой фиче — `domain` (типы + правила), `repository` (интерфейс + postgres),
   `service` (use-case, без HTTP/SQL-драйвера), `transport/http` (тонкий перевод).
6. Собери все в `main.go`, добавь мигратор, healthcheck, graceful shutdown.
7. Напиши `scripts/e2e.sh` раньше, чем обрастешь фичами: дымовой тест ловит
   регрессии дешевле unit-зоопарка.
8. Добавь мок второй бинарью: сначала `auto`, потом `manual/rejecting/failing`.
9. Прогони все запросы руками через curl (как раздел 8): 400/404/409 должны
   отличаться от 500 осмысленно.
10. Удали мертвое: `rg` по каждому экспорту, все, что не вызывается, — вон.
11. Унифицируй комментарии: «почему», а не «что», один язык, один тон.
12. Запакуй в Docker: мультистейдж, healthcheck с `wget`, env-дефолты, volume для PG.

## 9. Что осознанно осталось за рамками (и почему это не баг)

- **Аутентификация.** `X-User-ID` — заглушка из ТЗ («авторизацию реализовывать не
  нужно»). В проде перед API встанет gateway с JWT, а сервис уже принимает
  пользователя из заголовка — менять бизнес не придется.
- **Outbox + воркеры.** Интеграция синхронная: заказ создается, ресторан зовется
  сразу, падение фиксируется в `integration_failed` + `retry`. Для MVP и демо
  этого достаточно; путь к асинхронности (outbox, ретраи с бэкоффом, circuit
  breaker) описан в README как следующий шаг, а не как недоделка.
- **Метрики/трейсинг.** Есть request_id, структурные логи, healthcheck. Prometheus
  и OpenTelemetry — следующий слой, когда появится оркестрация.
- **Поиск и фильтры каталога.** Есть `open/available/limit/offset`. Полнотекст
  и гео — отдельная история с индексами, не MVP.

## 10. Глоссарий для новичка

- **Composition Root** — единственное место сборки зависимостей (`main.go`).
- **Vertical Slice** — фича как папка со своим domain/service/repository/transport.
- **Sentinel error** — именованная ошибка-маркер (`ErrNotFound`), маппится в HTTP-код.
- **Идемпотентность** — повтор запроса дает тот же результат без дублей.
- **Снепшот** — замороженная копия цены/названия в заказе, переживает правки меню.
- **Partial unique index** — уникальность только для не-NULL (`event_id`).
- **`SELECT ... FOR UPDATE`** — блокировка строки от гонок под транзакцией.
- **Graceful shutdown** — дождаться живых запросов перед выключением.
